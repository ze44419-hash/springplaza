# سبرينج بلازا كافيه — نظام إدارة الكافيه (Offline-First)

نظام متكامل لإدارة الكافيه: شاشة الكابتن، شاشة الكاشير (POS)، ولوحة تحكم المدير. **الواجهة بالكامل عربي (RTL)** مع دعم العمل بدون إنترنت ومزامنة تلقائية عند رجوع الاتصال.

**التقنيات:** Next.js 14 (App Router) · Tailwind CSS · Lucide Icons · Supabase (PostgreSQL + Auth + Realtime + Storage) · Dexie.js (IndexedDB)

---

## 1) التشغيل السريع

```bash
npm install
cp .env.example .env.local      # ثم املأ بيانات Supabase (واسم الكافيه والعملة)
npm run dev                     # للتطوير
# للإنتاج (وضع الأوفلاين يحتاج نسخة الإنتاج لأن Service Worker يُسجَّل فيها فقط):
npm run build && npm start
```

### إعداد Supabase (مرة واحدة)

1. أنشئ مشروعًا جديدًا في Supabase.
2. من **SQL Editor** نفّذ بالترتيب (لو كنت منفّذ نسخة قديمة من `001_schema.sql` أنشئ مشروعًا جديدًا أو نفّذ فقط جزء `receipt_templates` وسياساته):
   - `supabase/migrations/001_schema.sql` ← الجداول + RLS + الدوال + Storage + Realtime
   - `supabase/migrations/002_seed.sql` ← (اختياري) بيانات تجريبية: طاولات، منيو، مكوّنات، وصفات
   - `supabase/migrations/004_…sql` ← مخازن متعددة وسحوبات الكاشير وتعديل الأوردرات
   - `supabase/migrations/005_roles_accountant_hall.sql` ← دورا «محاسب» و«مسؤول القاعة» (**شغّله لوحده وانتظر نجاحه**)
   - `supabase/migrations/006_hall_accounting.sql` ← القاعة والحجوزات + المحاسبة وتوزيع الأرباح (**في تشغيل منفصل بعد 005**)
   - `supabase/migrations/007_hall_seed.sql` ← (اختياري) أسعار قاعة وأطباق وخدمات تجريبية
3. **أول أدمن:** من *Authentication → Users → Add user* أنشئ مستخدمًا (Auto-confirm)، ثم عدّل الإيميل في `supabase/migrations/003_bootstrap_admin.sql` ونفّذه.
4. من *Authentication → Providers → Email* **أوقف** خيار "Allow new users to sign up" (الحسابات تُنشأ من لوحة الأدمن فقط).
5. من *Project Settings → API* انسخ `URL` و `anon key` و `service_role key` إلى `.env.local`.
   - ⚠️ مفتاح `service_role` يُستخدم فقط داخل `src/app/api/admin/users/route.ts` (سيرفر) ولا يصل للمتصفح أبدًا.

بعدها ادخل بحساب المدير ← **الحسابات** ← أنشئ حسابات الكاشير والكباتن.

## 2) الأدوار والصلاحيات (RBAC + RLS)

| الدور | يدخل على | يستطيع |
|---|---|---|
| **admin** (مدير) | كل الشاشات | المنيو، المخزون، الوصفات، الحسابات، التقارير، **القاعة والمحاسبة** |
| **hall_manager** (مسؤول القاعة) | `/hall` | تقويم الحجوزات وحاسبة التكلفة، تعديل أسعار الإيجار والأطباق والخدمات |
| **accountant** (محاسب) | `/accounting` | الإيرادات والمصروفات وصافي الربح، الشركاء، توزيع الأرباح (قراءة فقط للحجوزات والأسعار) |
| **cashier** (كاشير) | `/cashier` | استقبال أوردرات الكباتن، **فتح أوردرات من شاشته**، تغيير الحالة، الدفع، الطباعة، فتح الشيفت وتسليمه |
| **waiter** (كابتن) | `/waiter` | إرسال الأوردرات ومتابعة أوردراته فقط |

> الدور اسمه في قاعدة البيانات `waiter` لكنه يظهر في كل الواجهات باسم **كابتن** (الترجمة في `roleLabel` داخل `src/lib/format.ts`).

الحماية على مستويين: `middleware.ts` (توجيه حسب الدور) و **Row Level Security** في قاعدة البيانات (الحماية الحقيقية).
كل الكتابة على الطلبات والورديات والمخزون تمر عبر دوال `SECURITY DEFINER` فقط (لا يوجد INSERT/UPDATE مباشر على `orders`):

| الدالة | الوظيفة |
|---|---|
| `create_order(jsonb)` | إنشاء طلب (idempotent — الـ id يُولَّد في الجهاز) وإعادة حساب الأسعار من السيرفر |
| `set_order_status(id, status)` | new → preparing → ready / cancelled |
| `pay_order(id, method, tendered, discount)` | الدفع + إكمال الطلب + **خصم المخزون حسب الوصفة** في نفس المعاملة |
| `open_shift` / `close_shift` | الشيفتات وحساب النقدية المتوقعة |
| `record_inventory_tx(...)` | شراء / مرتجع مورّد / تسوية جرد / تالف (على مخزن محدد) |
| `transfer_stock(...)` | تحويل خامة بين مخزنين (أدمن) |
| `create_withdrawal(...)` / `settle_withdrawal(...)` | سحب الكاشير من المخزن / الإرجاع وإقفال السحب |
| `admin_edit_order(jsonb)` | تعديل أوردر (أدمن) مع إعادة حساب المخزون للمدفوع |
| `sales_report(from, to)` | تقرير المبيعات (أدمن فقط) |

| `hall_quote` / `hall_save_booking` / `hall_set_booking_status` | حاسبة الحجز وحفظه وتغيير حالته (أدمن / مسؤول القاعة) |
| `accounting_summary(from, to)` / `distribute_profit(from, to, note)` | ملخص المحاسبة لأي فترة / اعتماد توزيع الأرباح (أدمن / محاسب) |

> التفاصيل الكاملة للقاعة والمحاسبة (الجداول، المعادلات، الصلاحيات، الشاشات) في **`docs/HALL_ACCOUNTING_AR.md`**.

## 3) كيف يعمل وضع الأوفلاين

```
Waiter/Cashier action ─▶ IndexedDB (orders + outbox) ─▶ UI يتحدث فورًا
                                   │
                    online? ──────▶ sync engine ──▶ Supabase RPC (بالترتيب)
```

- **الملفات:** `src/lib/db.ts` (Dexie) · `src/lib/outbox.ts` · `src/lib/sync.ts` · `src/lib/orders.ts`
- كل عملية كتابة تُحفظ في جدول `outbox` وتُرسل **بالترتيب** (طلب ← تغيير حالة ← دفع).
- الـ id يُولَّد في الجهاز، لذلك إعادة المحاولة بعد انقطاع الرد **لا تكرر الطلب ولا تخصم المخزون مرتين**.
- أخطاء الشبكة / 5xx / انتهاء الـ JWT ← إعادة محاولة تلقائية مع backoff (حتى 60 ثانية).
- أخطاء العمل (منتج اتحذف، لا توجد وردية…) ← تُوضع كـ `failed` وتظهر في الشريط العلوي مع أزرار **Retry / Discard**.
- المنيو والطاولات تُخزَّن محليًا وتتحدث عند رجوع الاتصال.
- الطلب قبل المزامنة يظهر برقم محلي `L-3F9A`، ثم يأخذ رقمه الرسمي `#1042` بعد المزامنة.
- تنبيهات Realtime تعمل عبر قناة `postgres_changes` على جدول `orders`، ومع كل (إعادة) اشتراك يتم جلب تعويضي للطلبات الفائتة.

**مهم لتجهيز الجهاز للأوفلاين:** افتح الشاشة (waiter / cashier) **مرة واحدة وأنت أونلاين** بعد تسجيل الدخول، ليُحفظ المنيو والصفحة في الكاش. الـ Service Worker (`public/sw.js`) يعمل في نسخة الإنتاج فقط.

## 3.5) الكاشير يفتح أوردرات + تسليم الشيفت

**أوردر من الكاشير:** زر **أوردر جديد** في شريط الشيفت يفتح نفس شاشة الكابتن (اختيار طاولة/تيك أواي/دليفري ← المنيو ← الإضافات ← إرسال) داخل شاشة الكاشير (`src/components/OrderTaker.tsx` مشترك بين الشاشتين). الأوردر يظهر في عمود «جديد» ويعمل أوفلاين مثل أوردرات الكباتن.

**تسليم الشيفت:** زر **تسليم الشيفت** ← يكتب الكاشير النقدية اللي عدّها ← يظهر الفرق (مظبوط / زيادة / عجز) ← **يُطبع إيصال التسليم تلقائيًا** (58/80 مم) ويحتوي على:

- اسم الكاشير + بداية ونهاية الشيفت
- عدد الأوردرات، مبيعات كاش، مبيعات كارت، الخصومات، إجمالي المبيعات
- حساب الدرج: رصيد أول الشيفت + مبيعات الكاش = المتوقع، مقابل الفعلي، والفرق
- الأصناف المباعة بالكمية والقيمة
- خانتا توقيع المسلِّم والمستلم

يتنبه الكاشير لو فيه أوردرات لسه مفتوحة قبل التسليم. التسليم يشتغل أوفلاين (يُرسل `close_shift` عند رجوع الاتصال) ويمكن إعادة طباعة الإيصال من نافذة التأكيد. الكود: `src/lib/shift.ts` و `ShiftReceipt` في `src/components/Print.tsx`.

## 3.6) الطباعة التلقائية عند الكاشير

أول ما الكابتن يبعت أوردر جديد، شاشة الكاشير تطبع **تذكرة الأوردر** (إيصال الكاشير) لوحدها على الطابعة الحرارية:

- التشغيل/الإيقاف من مفتاح **طباعة تلقائية** في شريط الشيفت (يُحفظ لكل جهاز، وهو شغّال افتراضيًا).
- الطباعة بالترتيب (طابور): لو وصل 3 أوردرات مع بعض يطبعوا واحد ورا التاني ولا يتداخلوا مع إيصال بيتطبع.
- كل أوردر يُطبع **مرة واحدة فقط** (يتحفظ رقمه على الجهاز) حتى لو الصفحة اتعملها Refresh أو الإنترنت رجع. ولا تُطبع الأوردرات الأقدم من 3 ساعات.
- أوردرات الكاشير نفسه لا تُطبع تلقائيًا (له زر طباعة يدوي). لو عندك أكتر من جهاز كاشير، شغّل الطباعة التلقائية على جهاز واحد بس.
- على الكارت يوجد زرّان: **حساب العميل** (فاتورة) و**تذكرة الأوردر**.

> ⚠️ **مهم — الطباعة بدون نافذة تأكيد:** المتصفحات تعرض نافذة الطباعة دايمًا. علشان تطبع مباشرة بدون أي ضغطة، شغّل Chrome/Edge على جهاز الكاشير بالخيار `--kiosk-printing` واجعل الطابعة الحرارية هي الطابعة الافتراضية. مثال على ويندوز: `chrome.exe --kiosk-printing --app=https://your-domain/cashier`.

## 3.7) تصميم الإيصالات (من لوحة المدير)

صفحة **المدير ← تصميم الإيصالات** فيها تصميمان منفصلان، لكل واحد معاينة مباشرة على ورق 58 أو 80 مم وزر طباعة تجريبية:

| التصميم | يُطبع إمتى |
|---|---|
| **إيصال الكاشير (تذكرة الأوردر)** | تلقائيًا عند وصول أوردر من كابتن |
| **حساب العميل (الفاتورة)** | عند الدفع أو زر طباعة الحساب |

القابل للتعديل: اسم الكافيه والعنوان والتليفون والشعار، المحاذاة، حجم الخط (صغير/متوسط/كبير)، الخط العريض للأصناف، شكل الفاصل، **اللي يظهر** (التاريخ، رقم الأوردر، الطاولة، اسم الكابتن، اسم الكاشير، الأسعار، الإضافات، الملاحظات، المجموع والخصم، طريقة الدفع)، نص التذييل، عدد النسخ، والسطور الفاضية قبل القص.
التصاميم تُحفظ في جدول `receipt_templates` وتُخزَّن محليًا على كل جهاز فتشتغل الطباعة أوفلاين بآخر تصميم محفوظ. الكود: `src/lib/receipt.ts` و `src/components/ReceiptView.tsx` و `src/app/admin/receipts/`.

## 3.9) السرعة

- **الـ middleware بدون استعلام قاعدة بيانات**: الدور وحالة التفعيل مخزَّنين في `app_metadata` للمستخدم (يُكتبوا من `/api/admin/users`). الحساب القديم بدون metadata يرجع لاستعلام واحد.
- استعلامات IndexedDB كلها بفهارس (`status` و `created_at` و `shift_id`) بدل قراءة الجدول كله.
- بطاقات الأوردرات وبلاطات المنتجات `React.memo` فالضغط على صنف يحدّث بلاطته فقط.
- أحداث Realtime من نوع UPDATE تُطبَّق محليًا بدون طلب شبكة؛ المنيو يُحدَّث مرة كل دقيقة بحد أقصى.
- شاشة «أوردر جديد» عند الكاشير تُحمَّل عند الطلب (`next/dynamic`) وكل صفحة لها JS مستقل.
- الصور تُصغَّر عند الرفع (WebP بعرض 640px) وتُحمَّل `lazy`.

## 3.12) المخازن المتعددة + سحب الكاشير (عهدة الباريستا) + تعديل الأوردرات

> **مهم:** نفّذ `supabase/migrations/004_warehouses_withdrawals_order_edit.sql` في SQL Editor بعد 001–003. آمنة على بيانات موجودة: أرصدة الخامات الحالية بتتنقل تلقائيًا لمخزن اسمه «المخزن الرئيسي».

**المخازن (أدمن ← المخازن والمخزون ← تبويب «المخازن»):** ضيف أي عدد من المخازن. كل خامة ليها رصيد في كل مخزن، والشراء/التالف/المرتجع/الجرد بيتسجّل على مخزن محدد، وفي زرار **تحويل** بين مخزنين. أول مخزن في الترتيب هو الافتراضي.

**سحب الكاشير:** من شاشة الكاشير زرار **المخزن ← سحب جديد**: يختار المخزن والخامات والكميات (مثلًا 1 كيلو بن). بيتسجّل **اسم الكاشير** والوقت. بعدها:
- كل أوردر بيتدفع بيتحسب تلقائيًا (حسب الوصفات) على السحب المفتوح — سحب الكاشير نفسه الأول ثم الأقدم.
- **الباقي مع الباريستا = اتسحب − اتصرف في الأوردرات − رجع.**
- **رجّع / قفّل السحب:** الكاشير بيكتب الكمية الراجعة للمخزن (ممكن على دفعات). لو قفل السحب، أي كمية مش راجعة ومش في مبيعات بتتسجّل **عجز** وبتتخصم من المخزون.
- الأدمن بيشوف كل السحوبات (مين سحب، رجّع إيه، فاضل كام، العجز) من تبويب «سحب الكاشير (العهدة)»، وفي جدول الخامات عمود «في المخازن» و«مع الباريستا».
- لو مفيش سحب مفتوح، البيع بيخصم من المخزن الرئيسي مباشرة (زي الأول).
- القاعدة الثابتة: `إجمالي الخامة = Σ أرصدة المخازن + Σ الباقي مع الباريستا`.
- شاشات المخزن محتاجة إنترنت (مش في طابور الأوفلاين).

**تعديل الأوردرات (أدمن ← الأوردرات):** اختار اليوم → «تعديل»: الأصناف (زيادة/نقص/حذف/إضافة صنف)، الإضافات، ملاحظات الصنف والأوردر، الصالة/تيك أواي/دليفري والطاولة، الحالة، الخصم، طريقة الدفع والمبلغ المستلم، أو **إلغاء الأوردر**.
- الصنف القديم بيحتفظ بسعره وقت الطلب؛ الصنف المضاف بيتسعّر بسعر المنيو الحالي.
- الأوردر **المدفوع**: تعديل الأصناف أو الإلغاء بيرجّع المخزون القديم لمكانه (للسحب أو المخزن) ويخصم الجديد، والمبيعات بتتحدّث.
- كل تعديل بيتسجّل في `order_edits` (قبل/بعد + مين عدّل)، وشاشات الكاشير بتتحدّث لحظيًا.
- تنبيه: لو عدّلت أوردر مدفوع في شيفت اتسلّم، تقرير المبيعات بيتغيّر لكن «المتوقع في الدرج» اللي اتسجّل وقت التسليم بيفضل زي ما هو.

## 6) خصم المخزون حسب الوصفة

```
استهلاك المكوّن = Σ ( كمية الصنف في الطلب × الكمية المطلوبة من المكوّن في الوصفة )
```

مثال (من البيانات التجريبية): طلب = 2 قهوة تركي + 1 لاتيه ← يُخصم **38 جم بن، 40 جم سكر، 200 مل حليب**، ويُسجَّل كل خصم في `inventory_transactions` من نوع `sale` مرتبطًا برقم الطلب.
المخزون يُسمح له بالنزول تحت الصفر (حتى لا يتعطل البيع لو نسي أحد تسجيل مشتريات) — ويظهر فورًا في تنبيهات النقص.

## 7) ما تم اختباره وما لم يتم

- ✅ `tsc --noEmit` بدون أخطاء، و `next build` نجح (بعد استبدال خطوط Google مؤقتًا بسبب عدم وجود إنترنت في بيئة الإنشاء) — يعني كل صفحات الـ CSS Modules و Tailwind تُترجَم سليمة.
- ✅ اختبار سياسات `receipt_templates`: الأدمن فقط يكتب، الكاشير والكابتن يقرؤون، والكاشير يقرأ أسماء الموظفين.
- ✅ تشغيل ملفات SQL (بالبيانات التجريبية العربية) على PostgreSQL 16 مع محاكاة لمخطط `auth`، واختبار: إنشاء الطلب (idempotent)، منع الكابتن من الدفع أو رؤية أوردرات غيره، الدفع بدون وردية، تكرار الدفع بدون خصم مزدوج، خصم الوصفة، تسليم الشيفت، التقرير، ومنع المستخدم المعطّل.
- ⚠️ **لم يتم** تشغيل `next build` ولا اختبار الواجهة في متصفح (بما في ذلك شكل الـ RTL، **الطباعة التلقائية**، وطباعة الإيصال العربي على الطابعة الحرارية، وأداء الصفحة على أجهزتك الفعلية) ولا مع مشروع Supabase حقيقي (بيئة الإنشاء بدون إنترنت مفتوح). جرّب على مشروع Supabase تجريبي أولًا، خصوصًا: Realtime، رفع الصور، والطباعة على طابعتك.

## 8) حدود معروفة

- شاشة الأدمن تحتاج إنترنت (الأوفلاين مخصص للكابتن والكاشير).
- الكابتن يرى إشغال الطاولات لأوردراته هو فقط (بسبب RLS)؛ الكاشير والمدير يرون الكل.
- التعديلات المتزامنة على نفس الطلب من جهازين: آخر كتابة تكسب.
- المعدّلات (Modifiers) عامة لكل المنتجات، وليست مربوطة بمنتج معين.
- الأرقام تظهر بالأرقام اللاتينية (0-9) عمدًا لسهولة القراءة على الإيصالات؛ لتغييرها عدّل `LOCALE` في `src/lib/format.ts`.
- نصوص رسائل الأخطاء القادمة من قاعدة البيانات تُترجم عبر `arabicError` في `src/lib/util.ts`؛ أي رسالة جديدة تضيفها في SQL أضف لها ترجمة هناك.

## المود الليلي (Night mode)
- زرار الشمس/القمر موجود في هيدر كل الصفحات وفي صفحة الدخول. الاختيار بيتحفظ على الجهاز (`localStorage: sp-theme`)، ولو ما اخترتش بيتبع إعداد الجهاز.
- كل الألوان في `src/app/globals.css` (`:root` للنهاري و `:root[data-theme='dark']` لليلي). عدّل اللون هناك مرة واحدة وهيتغير في كل مكان.
- الإيصالات المطبوعة ومعاينة الورقة بتفضل أبيض وأسود دايمًا.
- مكونات صفحة الدخول: `components/ui/elegant-dark-pattern.tsx` (الخلفية) و `components/ui/modern-stunning-sign-in.tsx` (الكارت) و `components/ui/theme-toggle.tsx` (الزرار).

## الطباعة التلقائية بدون نافذة
المتصفح بيعرض نافذة Print لأي `window.print()`، وده مش قابل للتخطي من الكود. الحل: افتح الكاشير بوضع الطباعة الصامتة عن طريق `start-cashier-printing.bat` (Chrome بخاصية `--kiosk-printing`) وخلّي طابعة الإيصالات هي الافتراضية في ويندوز.
مقاس الورق وكل تفاصيل الإيصال بتتحدد من الأدمن → تصميم الإيصالات (أي رقم بالمليمتر).
